# Visual Reference Corpus

An independent set of table layouts, built by designing them visually rather than by choosing among algorithm outputs. No layout algorithm of this project (v1, v2, min-height) was run to produce, select or score anything here.

Research brief: [`../VISUAL_RESEARCH.md`](../VISUAL_RESEARCH.md).

**Model:** `workbuddy-ai/deepseek-v4.1-flash-sg` through Pi (`pi -p`, every call a fresh, tool-less, session-less context, thinking `high` for design and review). Vision was checked first: the model correctly read random codes, numbers and colours from a rendered table. It also hallucinated a duplicate table in one test, which is why every geometry fact is measured, not taken from the model.

## Layout

```
manifest.json            families, splits and scenarios (generated by tools/manifest.mjs)
tables/new/*.json        65 table families written for this corpus (Pi from tables/briefs.js), structurally validated
tables/existing/*.json   74 families from ../data (used during algorithm development → research split only)
corpus/<split>/*.json    one record per scenario (schema below)
corpus/<split>/img/      real Chromium renders of every recorded layout
corpus/index.json        index + coverage + audit (tools/index.mjs)
corpus/holdout/FROZEN.json  sha256 of every holdout file, written before any algorithm sees them
runs/<scenario>/         resumable state, every prompt/raw reply (log-*.json) and every intermediate render
```

**Splits are by family.** All widths and font sizes of one table stay in the same split:

| Split | Families |
|---|---|
| `research` | the 74 tables that the existing algorithms were developed on |
| `validation` | half of the 65 new tables |
| `holdout` | the other half, alternating within each structure type so both splits cover all structures |

## How one scenario is built (`tools/design.mjs`)

A scenario is a table + available width + font size + scroll policy. Each one goes through these steps:

1. **Overview render.** Every cell on one line, plus measured content facts per column (longest unbreakable word, one-line width). No algorithm output is shown.
2. **Understanding and three designs.** The model explains what the table is for, how it is read, which columns belong together, what must stay intact and what may wrap. It then proposes three genuinely different width designs.
3. **Critique and revise, up to 3 rounds.** Every design is rendered in Chromium and the screenshots go back to the model, which names visual faults and their causes, then refines or tries new ideas until it declares no further improvement.
4. **Final selection** over all renders:
   - preferred design(s), acceptable alternatives, and bad designs with reasons;
   - a deliberately bad but plausible "contrast" design if none of the candidates is clearly bad;
   - a width range per column, rationale, general vs case-specific principles, trade-offs and open questions.
5. **Two independent blind reviews**, each in a fresh context:
   - candidates are relabelled A, B, C… in a different random order for each review;
   - two neutral references are mixed in: the browser's `table-layout:auto` and equal widths;
   - every layout is rated `excellent` / `good` / `acceptable` / `poor` / `bad`; ties and "unsure" are allowed.
6. **Status:**
   - `confirmed`: both reviewers grade the preferred design ≥ good;
   - `contested`: one reviewer does;
   - `rejected`: neither does.

   Rejected scenarios can be redesigned once from scratch with the reviewers' criticism as input (`--redo-rejected`); the first attempt is kept in `runs/<id>/state-attempt1.json`. Disagreements are recorded, not resolved.

**Hard constraints are enforced by code, not by the model:**
- column count;
- a minimum column width;
- total width ≤ available width for `fit` scenarios (`scroll-allowed` scenarios may exceed it);
- identical content, font, size, padding, borders, colours and alignment across all layouts.

Only column widths vary.

## Record schema (`corpus/<split>/<id>.json`)

| Field | Contents |
|---|---|
| `table` | `html` / `md`, `lang`, `structure`, `rowHeader`, `source`, `brief` |
| `conditions` | `availableWidth`, `fontSize`, `policy`, CSS, browser, `contentFacts` |
| `understanding` | purpose, reading pattern, column groups, what to keep intact, what may wrap |
| `preferred[]`, `acceptable[]`, `bad[]` | each with `colWidths` (rendered border-box px), `requestedWidths`, `tableWidth/Height`, `rowHeights`, `cellLines` `[row, col, lines]`, `overflow`, `screenshot`, `note`; `bad[]` adds `why` |
| other judgements | `ranges` (per column), `rationale`, `principles` {general, specific}, `tradeoffs`, `uncertain` |
| `designHistory` | every round's critique and design names |
| `review` | `verdict` {status, per-review grades of preferred / browser auto / equal widths}, raw blind ratings mapped back to design names |
| `provenance` | model, Pi version, timestamp |

To reproduce a layout, render `table` at `conditions` with `<colgroup>` widths = `colWidths` and `table-layout:fixed`; `tools/render.mjs` does exactly this.

## Run

```bash
node tools/gen-tables.mjs                                  # expand briefs → tables/new (resumable)
node tools/manifest.mjs                                    # families, splits, scenarios
node tools/design.mjs --split holdout,validation --jobs 8  # resumable; --only id1,id2  --limit N  --rounds 3
node tools/design.mjs --split holdout,validation --redo-rejected
node tools/freeze.mjs                                      # freeze holdout (then: --verify)
node tools/design.mjs --split research --jobs 8
node tools/index.mjs                                       # index + coverage + audit
```

All dependencies are project-local (`../node_modules/playwright-core`, Playwright's cached Chromium). Pi is used as installed; no Pi configuration is changed.

## Limits

- These are one model's visual design judgements, checked by two more contexts of the same model. Same-model review gives only limited independence. They are reference judgements, not objective aesthetic truth and not human preference or reading-speed data.
- The new tables were written by the same model from short briefs. They are realistic but not sampled from real documents.
- Only Chromium on macOS system fonts was used.
